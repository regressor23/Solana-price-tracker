# SOL Warzone — план реалізації

Візуалізація живого потоку ордерів **SOL/USDC** у вигляді 3D-битви:
**Орки** (червоні, ведмеді/продавці) проти **Протосів** (зелені, бики/покупці).

---

## 1. Аналіз відео (`Nl4BOwml8Lmb-8_J.mp4`)

18 секунд, 1562×1136, ~30fps. Це **не** xrpwarzone — це полірованіша версія тієї ж ідеї
на парі **BTC/USD · Aggregated Spot** (агрегація Binance + Bybit).

### Розкладка екрана

```
│ UTC 21:06:50    BTC/USD · AGGREGATED SPOT   MARKET PRESSURE   🔊 │

│                     -0.008% tick            Bybit · Liquidated…  │
├──────────────────────────────────────────────────────────────────┤
│ SELL WALL $64.0M                                BUY WALL $46.9M  │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│         3D поле бою (low-poly, орбітальна камера)                │

├────────────────────────────┬─────────────────────────────────────┤
│ ORDER BOOK DEPTH           │ MARKET FEED               LIVE      │

```

### Ключові механіки, зчитані з кадрів

| Елемент | Поведінка |
|---|---|
| **Лінія фронту** | Крива, що ділить зелену/червону територію. Зсувається у бік того, хто програє. |
| **Прапори баз** | `Bulls` (зелений) знизу, `Bears` (червоний) зверху — тримають кути карти. |
| **Юніти** | Сотні інстансованих моделей у строю (шеренги), маршують до фронту, б'ються. |
| **Спалахи** | Білі кулі світла на фронті = момент зіткнення / великого трейду. |
| **Стріли** | Білі траєкторії від далекобійних юнітів. |
| **Камера** | Плавно облітає карту, ~3 пресети ракурсів. |
| **Depth-графік** | Класична «долина» bid/ask, поточна ціна по центру, ±1% межі. |
| **Фід** | Ліквідації (з логотипом біржі) + великі трейди; кожна подія має ціну **в юнітах**. |

## 2. Реверс-інжиніринг `xrpwarzone.com`

Завантажив і розібрав бандли. Це чистий **Vite + vanilla TS + three.js**, без React.

```
index.html            25 KB    (3× JSON-LD, preconnect до Binance)
index-CX9nkck9.js    100 KB    ядро: маркет-дані, симуляція, HUD, чат
render3d-*.js        649 KB    three.js + GLTFLoader + DRACOLoader + InstancedMesh
index-BZab3JBx.css    45 KB
```

### Джерело даних

Браузер **напряму** тримає WebSocket до Binance — жодного бекенда:

```js
streamList() {
  return this.market.syms.flatMap(e => [
    `${e.sym}@aggTrade`,        // потік трейдів
    `${e.sym}@depth20@100ms`,   // 20 рівнів склянки, 10 Гц
    `${e.sym}@ticker`           // 24h статистика
  ]).join("/")
}
// wss://{host}/stream?streams=...
hosts: ["stream.binance.com:9443", "data-stream.binance.vision", "stream.binance.us:9443"]
```

Три хости з фолбеком → якщо всі впали, вмикається `goDemo()` (детермінований
seeded-RNG генератор, `new Tt(1)`), щоб картинка ніколи не була порожньою.

### Повний конфіг балансу (витягнутий з бандла)

```js
h = {

  whaleUsd: 60_000, heavyUsd: 15_000,

  relWhaleFloor: 9000,  relWhaleMult: 30,     // «кит»    = 30× від EMA

  minTroops: 40, baseTroops: 200,
  maxUnitsPerTrade: 60,
  usdPerReinforce: 1000,   // $ у склянці = 1 юніт підкріплення

  sepRadius: 1.7, sepForce: 34,               // boids-розділення

  filesPerRank: 40, fileSpacing: 2.1, rankSpacing: 2.2,
  roleDepth: { melee: 0, archer: 8, mage: 11 },  // шеренги в глибину
```

### Правила перекладу «ринок → бій»

1. `aggTrade` → **втрати**. Buy-трейд убиває `min(usd / 3800, 60)` юнітів Undead.
2. `depth20` → **підкріплення**. Bid-стіна ділиться на $1000 = черга нових юнітів Kingdom.
3. Дисбаланс bid/ask → **позиція лінії фронту** (`tugForce`, `tugMark`).
4. Трейд > 30× EMA → **кит**: вибух, 26–60 втрат, 22 підкріплення, спавн **чемпіона**.
5. Кожні 60 с (`candleSec`) — **раунд**. Хто вбив більше — `BUYERS WIN` / `SELLERS WIN`.
6. Волатильність → `intensity` → тряска камери, освітлення (`moodWarmth`, `moodDim`).

### Моделі (KayKit-стиль)

```
/models/kingdom/  Knight.glb  Rogue_Hooded.glb  Mage.glb
/models/undead/   Skeleton_Warrior.glb  Skeleton_Rogue.glb  Skeleton_Mage.glb
/models/wk/       sword_1handed  shield_{round,square,spikes,badge}  bow  staff  spellbook
/models/wu/       Skeleton_{Axe,Blade,Crossbow,Staff,Shield_*}
```
Зброя — окремі `.gltf`, кріпляться до кісток → 4 варіанти лицаря з 1 меша.

### Що ще є (варте копіювання)

- **Warzone-чат** з вибором сторони Bull/Bear, збереження в `localStorage` (`xb.warzone`)
- **Позиційний звук** через WebAudio: `melee_1..5`, `bow`, `champion`, `verdict_win`, фільтри `lowpass/bandpass`
- **Fallback HUD** — 2D-режим, якщо WebGL недоступний
- **Мобільна версія** — окремий bottom-sheet (`mobileSheetBackdrop`, `mobileTugForce`)
- **A11y** — `aria-live`, `role="status"`, повна клавіатурна навігація

## 3. Головна проблема адаптації

> **На Solana немає біржової склянки.** Jupiter — це агрегатор AMM-роутів, а не order book.

Отже `depth20@100ms`, `SELL WALL $64.0M`, «долина» bid/ask — **не існують**
у тому вигляді. Плюс друга відмінність: Binance WS — публічний і безлімітний,
тому xrpwarzone обходиться без бекенда. **Jupiter має рейт-ліміти**, тож
підключати кожного відвідувача напряму не можна.

### Рішення

| Оригінал | Заміна на Solana |
|---|---|
| `depth20@100ms` (склянка) | **Крива price-impact**: серія quote-запитів на зростаючі розміри → та сама «долина» |
| `SELL WALL / BUY WALL $` | **$ обсяг до 1% просадки** в кожен бік (з тієї ж кривої) |
| `aggTrade` (потік трейдів) | **Свопи з пулів** через Helius WS / Yellowstone gRPC (Тир B) або тік-дельти ціни (Тир A) |
| Ліквідації з Bybit/Binance | **Jupiter Perps / Drift** ліквідації (опційно, Тир C) |
| Прямий WS з браузера | **Один бекенд-колектор → власний WS фан-аут** на всіх клієнтів |

## 4. Шар даних — перевірені ендпоінти

Усе нижче я **реально викликав**, воно працює без API-ключа.

```

```

### 4.1 Ціна — `lite-api.jup.ag/price/v3`

```bash
curl "https://lite-api.jup.ag/price/v3?ids=So11111111111111111111111111111111111111112"
```
```json
{"So111...112": {
  "usdPrice": 76.51048311238718,
  "blockId": 438416423,
  "liquidity": 668179929.69,
  "priceChange24h": -0.12394688558977165,
  "decimals": 9
}}
```
`blockId` — дедуплікація тіків. Опитувати 1–2 Гц з бекенда.

### 4.2 Свічки — `datapi.jup.ag/v2/charts` ⚠️ timestamps у **мілісекундах**

```bash
curl "https://datapi.jup.ag/v2/charts/${SOL}?interval=1_MINUTE&baseAsset=${SOL}\
&from=1786367000000&to=1786370600000&candles=60&type=price"
```
```json
{"candles":[{"time":1786367940,"open":76.6697,"high":76.6938,
             "low":76.6425,"close":76.6756,"volume":125799.16}, …]}
```
З секундами повертає `{"candles":[]}` — це головна пастка. Для прогріву стану
при завантаженні сторінки (щоб битва починалась не з нуля).

### 4.3 «Глибина» — драбина quote-запитів ⭐ ключова знахідка

```bash
curl "https://lite-api.jup.ag/swap/v1/quote?inputMint=${SOL}&outputMint=${USDC}\
&amount=10000000000&slippageBps=5000"
```

Мій реальний замір (SOL @ $76.55):

| Розмір | Отримано USDC | Сер. ціна | Price impact |
|---:|---:|---:|---:|
| 10 SOL | 765.52 | 76.5521 | 0.000% |
| 100 | 7,655.03 | 76.5503 | 0.001% |
| 1,000 | 76,546.31 | 76.5463 | 0.006% |
| 10,000 | 765,287.37 | 76.5287 | 0.029% |
| 50,000 | 3,814,201.71 | 76.2840 | **0.349%** |

Дзеркальний виклик `USDC → SOL` дає bid-сторону. Разом — **точний аналог
«долини» зі склянки**, і навіть чесніший: він показує реальну виконувану
ліквідність по всіх DEX-ах Solana.

`routePlan` бонусом дає назви DEX-ів (`HumidiFi`, `Orca`, `Raydium`, `Meteora`) —
можна показувати як «бойові знамена» / джерела підкріплень.

**Ліміт:** 12 рівнів × 2 сторони = 24 запити. На безкоштовному тирі — не частіше
ніж раз на 3–5 с, і **лише з бекенда**. З ключем з `portal.jup.ag` (25M кредитів/міс
безкоштовно) можна щосекунди.

### 4.4 Пули — `datapi.jup.ag/v1/pools?assetIds={SOL}`

Повертає адреси пулів, DEX, ліквідність, обсяг 24h. Потрібно для Тиру B
(підписка на vault-акаунти).

### 4.5 Потік трейдів — три тири

| Тир | Джерело | Ключ | Що дає |
|---|---|---|---|
| **A** (MVP) | Дельти `price/v3` (1–2 Гц) + обсяг зі свічок | ні | напрям і сила тиску, без окремих трейдів |
| **B** (повний) | Helius WS `accountSubscribe` на vault-акаунти топ-пулів | так, free tier | **кожен своп**: розмір, напрям → кити, чемпіони |
| **C** (епік) | Jupiter Perps / Drift ліквідації | так | подія «Liquidated long/short» як у відео |

> ⚠️ Публічний `api.mainnet-beta.solana.com` я перевірив — **не відповідає**
> (блокує). Для Тиру B потрібен Helius / QuickNode / Triton. Helius free:
> 5 одночасних WS-з'єднань, кілька підписок на з'єднання — достатньо.

**Логіка Тиру B:** кожен своп змінює баланси двох token-акаунтів пулу.
`Δ(SOL vault) < 0` → хтось купив SOL (бики). Розмір дельти = обсяг трейду.
Агрегація 3–5 топ-пулів дає ~90% реального флоу.

## 5. Перекалібрування балансу під SOL

Абсолютні пороги з BTC не працюють: `whaleUsd: 60_000` для SOL — це не кит,
а звичайний трейд. **Використовувати лише відносні пороги** (вони вже є в конфігу):

```js
const cfg = {
  usdRefEma: 0.03,                              // EMA розміру трейду
  relHeavyFloor: 1_000,  relHeavyMult: 8,       // ↓ з 2500
  relWhaleFloor: 4_000,  relWhaleMult: 30,      // ↓ з 9000

  usdPerTroop: 900,        // ↓ з 3800 — SOL/USDC має менший тік-обсяг
  usdPerReinforce: 400,    // ↓ з 1000
  flowScale: 60_000,       // ↓ з 180_000

  poolPerSide: 250,        // лишити (це ліміт GPU, не ринку)
  maxUnitsPerTrade: 60,
  candleSec: 60,
}
```

Точні числа підбираються на живих даних: у моєму замірі 1-хв обсяг був
~$125k. Правильний шлях — **автокалібрування**: тримати EMA хвилинного
обсягу і виводити `usdPerTroop = volEMA / targetTroopsPerMin`.

## 6. Візуальна концепція

### Червона сторона — Орки (ведмеді / продавці)

- Земляно-червона територія, багнюка, кістки, тотеми, палісад із загострених колод
- Юніти: `Orc_Grunt` (melee), `Orc_Archer` (лук), `Orc_Shaman` (магія)
- Чемпіон: `Orc_Warchief` — вдвічі більший, бойовий барабан
- База: дерев'яна фортеця з черепами, дим від багать
- Ефекти: земляні вибухи, іскри, кров, warp-фрі — усе фізичне
- Палітра: `#8B1A1A` `#C4472C` `#2E1A12`, тепле помаранчеве світло від вогнищ
- Звук: барабани, роги, важкі удари металу об дерево, гортанні вигуки

### Зелена сторона — Протоси (бики / покупці)

> Назва **Protoss** — торгова марка Blizzard. У продакшені брати лише
> *естетику* (кристали, псіонічні клинки, warp-in, енергощити) з власним
> неймінгом: «Aetherium», «Ascendants», «The Nexus» тощо.

- Стерильна біо-люмінесцентна територія, гексагональна сітка, левітуючі плити
- Юніти: `Zealot` (псі-клинки), `Sentinel` (енергетичний стрілець), `Templar` (шторм)
- Чемпіон: `Archon` — куля плазми, світиться, освітлює поле навколо
- База: кристалічний пілон-нексус, промінь у небо
- **Warp-in замість спавну**: юніт матеріалізується з блакитного вихору за 0.4 с
- **Енергощит**: перед смертю ламається блакитна сфера (2-стадійна смерть → читабельніше)
- Палітра: `#00D4FF` `#7FFFD4` `#0A2A3A`, холодне бірюзове emissive-світло
- Звук: гул енергії, псіонічний дзвін, warp-шум, синтезовані голоси

### Поле бою

- Гексагональна нейтральна зона по центру, що «заражається» кольором переможця
- **Лінія фронту**: shader-маска між двома terrain-матеріалами, м'який градієнт
  ~4 юніти завширшки, анімована шумом
- Динамічне освітлення: `moodWarmth` → зсув до помаранчевого при домінуванні орків,
  до бірюзового при домінуванні протосів
- Небо: орківська сторона — грозові хмари; протоська — зоряна туманність

## 7. Архітектура

```
┌─────────────────────────────────────────────────────────┐
│  COLLECTOR (Node 22 + TS, 1 інстанс)                    │
│                                                         │
│  ├─ PriceFeed      poll price/v3       1 Гц             │
│  ├─ DepthFeed      quote-драбина 12×2  0.2–1 Гц         │
│  ├─ CandleFeed     datapi charts       1/хв (прогрів)   │
│  ├─ SwapFeed       Helius WS vaults    подієво [Тир B]  │
│  └─ Normalizer     → уніфікований MarketEvent[]         │
└────────────────────────┬────────────────────────────────┘
                         │ Redis pub/sub (опційно, для масштабу)
┌────────────────────────▼────────────────────────────────┐
│  WS GATEWAY (uWebSockets.js)                            │
│  broadcast бінарних кадрів, 10 Гц, snapshot на connect  │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────┐
│  CLIENT (Vite + TS + three.js, без фреймворку)          │
│                                                         │
│  ├─ MarketStore    буфер подій, інтерполяція            │
│  ├─ BattleSim      детерміністична симуляція, 30 Гц     │
│  │   ├─ Spawner    події → загони                       │
│  │   ├─ Steering   boids: seek/separate/arrive          │
│  │   ├─ Combat     слоти атак, HP, смерті               │
│  │   └─ FrontLine  tug-of-war позиція                   │
│  ├─ Renderer3D     InstancedMesh + GPU skinning         │
│  ├─ HUD            звичайний DOM, не canvas             │
│  ├─ AudioEngine    WebAudio, пул семплів                │
│  └─ Fallback2D     якщо WebGL недоступний               │
└─────────────────────────────────────────────────────────┘
```

**Хто рахує рахунок (рішення 13.08.2026).** Симуляція розділена на дві
половини, і межа проходить не там, де в схемі вище:

- **Сервер — власник рахунку.** Потік по сторонах, втрати, живі юніти,
  позиція лінії фронту, вердикт раунду. Це скалярний стан: рахувати дешево,
  а результат мусить бути однаковий для всіх.
- **Клієнт — власник видовища.** Позиції юнітів, boids, анімації, камера.
  Тут розбіжність між вкладками невидима і нікому не шкодить.

Причина: `RoundEnd` лежить у `ServerMessage`, тобто контракт уже казав
«сервер», тоді як схема вище ставила `BattleSim` цілком у браузер. Клієнти
підключаються в різні моменти й стартують із різних снапшотів, тож детермінізм
симуляції їх не врятує — у двох вкладках вердикти розійшлися б. Лічильники
армій для HUD (`C8`) з тієї ж причини теж серверні.

**Чому один колектор:** 1000 відвідувачів × 24 quote-запити = миттєвий бан.
Один колектор робить 24 запити на всіх і роздає результат через свій WS.
Це головна архітектурна відмінність від xrpwarzone.

## 8. Покроковий план

### Фаза 0 — Каркас (0.5 дня)
1. `npm create vite@latest sol-warzone -- --template vanilla-ts`
2. Монорепо: `apps/web`, `apps/collector`, `packages/protocol` (спільні типи подій)
3. ESLint + Prettier + Vitest, `.env.example` з `JUPITER_API_KEY`, `HELIUS_API_KEY`
4. Деплой-заглушка: Vercel (web) + Fly.io/Railway (collector)

### Фаза 1 — Дані, без графіки (1.5 дня)
5. `PriceFeed`: poll `price/v3`, дедуп по `blockId`, EMA, tick-%
6. `DepthFeed`: драбина `[10, 25, 50, 100, 250, 500, 1k, 2.5k, 5k, 10k, 25k, 50k]` SOL
   в обидва боки → нормалізована крива + `wallUsd` до ±1%
7. `CandleFeed`: 1-хв свічки за останню годину (пам'ятай про **ms**)
8. **Тест-сторінка**: голі числа на чорному фоні. Дивитись 30 хв, перевірити,
   що дані живі й адекватні. ⛔ Не йти далі, поки цей крок не стабільний.
9. Rate-limit guard: черга + backoff + кеш, fallback на останній валідний снапшот

### Фаза 2 — Протокол і WS-фан-аут (1 день)

> **Перероблено 13.08.2026 за вимірами.** Заміряно на проді: **597 B/s на
> клієнта** (2.05 МБ/год), знімок при підключенні 16.6 КБ. З усталеного
> трафіку **88.6% — це трейди**, і саме ті, яких клієнт більше не показує:
> у стрічку йдуть лише `heavy`+, решта 270 подій за хвилину потрібні тільки
> для агрегату. Пункти 11–13 нижче переглянуті через це.

10. **Агрегація дрібного потоку.** `heavy`+ ідуть поштучно, `normal` —
    зведенням (`buyUsd`, `sellUsd`, `trades`) замість окремих подій. Мінус
    ~85% трафіку без зміни формату. Симуляції поатомність дрібних трейдів
    не потрібна: при `poolPerSide: 250` і `usdPerTroop: 900` один трейд на
    $755 не відрізнити від двох по $377.
11. **Gateway лишається на `ws`.** `uWebSockets.js` — нативний аддон, який
    ускладнює збірку на Nixpacks і прив'язує до версії Node; чинне
    навантаження `ws` тримає без напруги. Міняти лише за заміряною
    проблемою, не за планом.
12. **Бінарна серіалізація відкладена до повторного виміру.** Обіцянка
    «5–10× трафіку» писалася до будь-яких вимірів. Після п.10 лишиться
    ~90 B/s, і рукописний `DataView` з тестами та ризиком розсинхрону
    версій має спершу довести, що окупається.
13. Reconnect з експоненційним backoff — **зроблено у фазі 0**. Demo-режим
    (seeded RNG) вмикається **лише при падінні апстріму**, без ручного
    тригера: стани HUD переглядаються в прев'ю дизайн-системи, а не в
    живому застосунку.
14. **Приземлити `tokens.css`** із дизайн-системи. Це самі змінні, без
    компонентів, тож `/debug` одразу отримує коректні токени, а паліта
    перестає жити у двох місцях.

### Фаза 3 — Двовимірний прототип видовища (2 дні)

> **Перероблено 13.08.2026.** Фаза 3 писалася як «найважливіша», бо мала
> відповісти на питання **чи роблять ринкові дані цікаву битву**. На це вже
> відповіли: рахунок рахує сервер (§7), а баланс закріплений інваріантами в
> replay-харнесі — втрати тримаються в межах ±20% від цілі, жодна сторона не
> залипає, збалансований ринок лишається контестним, однобічна година рухає
> фронт і тримає його там. Тюнити наосліп більше нема чого.
>
> Питання фази стало іншим і вужчим: **чи можна намалювати читабельну битву,
> маючи авторитетний лічильник?** Клієнт отримує `Pulse` десять разів на
> секунду — `orcAlive`, `nexusAlive`, `frontLine` — і мусить показати картинку,
> яка цим числам не суперечить.

14. `BattleField` на canvas2d: юніти — кольорові крапки, дві бази, смуга фронту.
15. **Узгодження з авторитетним лічильником — серцевина фази.** Сервер каже
    «орків стало 197 замість 203». Клієнт має прибрати шістьох так, щоб це
    читалося як бій: тих, що на фронті, зі смертю на місці — а не видалити
    шість випадкових крапок по всьому полю. Симетрично для приросту: юніт
    зʼявляється в базі й іде до фронту, а не матеріалізується в гущі.
16. **Розбіжність рахунку і картинки** — окремий стан, який треба спроєктувати.
    Якщо клієнт відстав (вкладка була у фоні, кадри пропущені), різниця може
    бути в десятки юнітів. Наздоганяти по одному — це хвилина брехні на екрані;
    доганяти миттєво — це стрибок. Потрібна межа, за якою клієнт визнає
    поразку і пересинхронізується різко.
17. Steering: seek → separate → arrive; шеренги (`filesPerRank: 40`). Мета —
    щоб маса читалася як дві армії, а не як хмара точок.
18. Інтерполяція між пульсами: 10 Гц даних проти 60 кадрів на секунду — шість
    кадрів на кожен пульс. `frontLine` їде плавно, лічильники не «тремтять».
19. **Тюнінг тут — читабельності, не балансу.** Питання не «чи справедливо»,
    а «чи видно, хто виграє, не дивлячись на цифри».

**Чого тут більше немає:** spawner за формулою `usd → units`, tug-of-war від
depth, раунди й вердикт, автокалібрування порогів. Усе це переїхало на сервер
у Фазі 2 і покрите тестами. Клієнт цих правил не знає й знати не повинен.

### Фаза 4 — 3D-рендер (3 дні)
21. three.js: сцена, `PerspectiveCamera`, 3 пресети, орбітальне слідування
22. Terrain: `PlaneGeometry` + noise-heightmap + shader-маска лінії фронту
23. `InstancedMesh` на роль×фракцію (6 мешів). Skinning — через texture-based
    animation (запекти анімації в текстуру) — інакше 500 skinned-мешів вб'ють FPS
24. GLTF + DRACO завантаження, прогрес-бар, таймаут 20 с → fallback
25. LOD: далекі юніти → біллборди
26. Частинки: warp-in, вибухи, стріли, псі-шторм — усе на GPU (`Points` + shader)

### Фаза 5 — Арт (3–4 дні, паралельно з Фазою 4)
27. Джерела моделей:
    - [Quaternius](https://quaternius.com/) — **CC0**, є Ultimate Modular Sci-Fi,
      Animated Robot, RPG-персонажі. Найкраще співвідношення ціна/якість.
    - [KayKit](https://kaylousberg.itch.io/) — CC0, точно той стиль, що у відео
    - [Poly Pizza](https://poly.pizza/) — агрегатор CC0
28. Ретаргет анімацій (idle, walk, attack, death, warp-in) в Blender → GLB
29. Оптимізація: `gltf-transform` → Draco + KTX2, ціль **<80 KB на юніт**
30. Матеріали: орки — rough/diffuse; протоси — emissive + Fresnel rim-light
31. Скайбокси, партикли, іконки DEX-ів

### Фаза 6 — HUD і звук (2 дні)
32. HUD у DOM (не canvas): ціна, tick-%, пресинг, стіни, лічильники
33. Крива ліквідності — SVG-path, перебудова на кожен depth-снапшот
34. Battle feed — віртуалізований список, макс 50 елементів
35. WebAudio: пул семплів, позиційність, `lowpass` за відстанню, глобальний mute
36. Мобільний bottom-sheet, портретна орієнтація

### Фаза 7 — Полірування (2 дні)

38. A11y: `aria-live` на фід, клавіатура, `prefers-reduced-motion` → без тряски
39. Перф-бюджет: 60 FPS на M1 / GTX 1650. Профілювати `InstancedMesh` draw calls

41. Sentry + аналітика; healthcheck колектора

### Фаза 8 — Опційне (за бажанням)
